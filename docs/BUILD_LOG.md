# Build Log

Chronological record of what was built, **why**, and which alternatives were rejected.
Read this before an interview to retell the story of the project.

| Step | What | Why / alternatives considered |
|------|------|-------------------------------|
| 1 | **Data warehouse.** Downloaded M5 (Kaggle `m5-forecasting-accuracy`). `retailpulse.data.ingest` reshapes the wide sales file (1,941 day columns) into a DuckDB star schema: `items`, `stores`, `calendar`, `prices`, `sales`. | **DuckDB** over Postgres/SQLite: it's embedded (no server), columnar and fast for analytics, and it reads CSV natively. A read-only connection is also a simple sandbox for the agent later. **The reshape runs in SQL (`UNPIVOT`), not pandas:** pandas `melt` on 59M rows needs several GB of RAM, while DuckDB streams it in 92s. **`revenue` is precomputed** in the fact table so the LLM doesn't need a three-way join for dollar questions. That means fewer chances for wrong SQL. |
| 2 | **Test fixture.** `scripts/make_fixture.py` cuts 105 series (3 stores × 5 items × 7 depts, last 730 days) in the *raw* M5 format (<1 MB). | Tests run the **real** ingest code on real-shaped data, so CI needs no Kaggle credentials and runs in seconds. The alternative was a mocked DB, but that wouldn't catch ingest bugs. |
| 3 | **Features** (`forecasting/features.py`): one DuckDB SQL query builds lags 28–56, 7/28/56-day rolling means, a 28-day std and zero-fraction, price ratio and week-over-week change, calendar/event/SNAP flags and item age. | **Direct 28-day strategy:** every feature looks ≥28 days back, so one model scores the whole horizon. The rejected alternative was a *recursive* model (lag-1 features, feeding predictions back), which compounds errors and needs 28 sequential calls at serving time. **Date-based `RANGE` windows** rather than row offsets, so gaps in a series can't shift a lag. **One query for train and serve**, which prevents training/serving skew without a feature store. |
| 4 | **Model** (`forecasting/train.py`): LightGBM, **Tweedie** objective, trained on 3 stores (one per state). The time split is train → 28-day validation (early stopping) → 28-day holdout → 28-day future. | **Tweedie vs MSE/Poisson:** retail demand is zero-inflated with a long tail. Tweedie (power 1.1) models that mass at zero and was the standard choice among top M5 solutions. **LightGBM vs deep learning (DeepAR/TFT):** it's faster to train on CPU, handles categoricals natively and is easy to explain, and gradient boosting won M5. **Two models:** *A* is trained without the last 56 days and gives an honest holdout score. *B* is refit on all data with A's best iteration count; it's the one deployed, so it uses the most recent demand. |
| 5 | **Evaluation:** WRMSSE (M5 metric, item×store level) plus MAE, RMSE and bias, compared with two baselines: a 28-day moving average and a 7-day seasonal naive. | A model is only worth deploying if it beats naive baselines. WRMSSE scales errors by each series' own volatility and weights them by revenue, so a 1-unit error on a $50 item matters more than on a $1 item. |
| 6 | **MLflow:** params, metrics, feature importance and the model are logged to a local SQLite store, and the model is registered as `retailpulse-demand`. The new version gets the **`champion` alias only if its holdout WRMSSE beats the current champion.** | This is a cheap version of a model-promotion gate. Serving loads `models:/retailpulse-demand@champion`, so promotion and rollback are alias moves with no code change. |
| 7 | **Forecasts published to DuckDB:** a `forecasts` table (backtest + future) and a `forecast_accuracy` view. | This lets the agent answer "how accurate was the forecast for FOODS in CA_1?" with plain SQL rather than a special tool. Only promoted models publish. |
| 8 | **Serving** (`forecasting/serve.py`): FastAPI with `/forecast` (item × store × ≤28 days) and `/what-if` (price change %). The model loads once at startup, and each request gets its own DuckDB cursor. | The what-if re-scores the horizon with the price features changed and history fixed, which approximates price elasticity *learned by the model*. It's a correlational estimate, not causal. |
| 9 | **Monotone price constraints, model v2.** Retrained with `monotone_constraints=-1` on the price features after v1's what-if produced backwards elasticities (see CHALLENGES #7). v2 was promoted by the champion gate. | **Results (3 stores, 9,147 series, 28-day holdout ending 2016-05-22):**<br>• WRMSSE: **0.823** model, 0.841 MA28, 1.076 seasonal naive.<br>• MAE 1.01, RMSE 1.97, bias −5.8%.<br>• Training takes ~6.5 min on a 12-core CPU, including 85 s of feature SQL. |
| 10 | **Inventory signals** (`data/inventory.py`). M5 has no stock data, so I derive it. If an item sells λ/day, a k-day zero run happens by chance with probability e^(−λk). Below 1% while the item is listed, it's flagged `likely_out_of_stock`; runs over 56 days are flagged `possibly_discontinued`. | Rejected: a fixed "N zero days" rule, which flags every slow seller. The Poisson rule adapts to each item's rate. **Full data:** 1,116 likely stockouts (~36k lost units) and 287 possibly discontinued, out of 30,490 series. |
| 11 | **SQL sandbox** (`tools/sql.py`). Four layers:<br>1. sqlglot parse: single SELECT only, table allow-list, blocked file/env functions.<br>2. DuckDB `read_only` plus `enable_external_access=false`.<br>3. Injected LIMIT, 200-row cap, and a timer that calls `interrupt()` after 20s.<br>4. `EXPLAIN` row-scan estimate; above 60M rows, a human must approve. | Defence in depth: the parser alone can be bypassed by exotic syntax, and the read-only connection alone still allows file reads. **The cost estimate uses DuckDB's own planner,** so a self-join of `sales` (94M rows) needs approval while a full-table aggregate (47M) does not. |
| 12 | **Tools** (`tools/registry.py`): `run_sql`, `forecast_item`, `price_what_if`, `create_chart`. They use strict JSON schemas. Errors are returned to the model as `is_error` tool results, never raised. | Tool descriptions say *when* to use each tool (e.g. aggregated forecasts → SQL on `forecasts`, single item → `forecast_item`). This is what tool-selection accuracy depends on. Returning errors lets the model self-correct, the "reflect" step. The forecast tools call the FastAPI service over HTTP, so the agent and the model deploy independently. |
| 13 | **LLM layer** (`llm/`). One `complete(system, messages, tools)` interface with three implementations:<br>• **Claude**, via the official Anthropic SDK: prompt-cached system prompt, `effort`, and server-side refusal fallback.<br>• **Ollama**, a local and free option that translates message formats.<br>• **Replay / Scripted**, for tests and CI. | Anthropic's message format is the canonical one, because it's the richest (thinking blocks, tool_use ids). Rejected: LangChain chat models, which add an abstraction layer I'd have to debug through and hide provider features like caching and effort. **The replay cassette is keyed by a hash of the full request,** so any prompt or tool change forces a re-record instead of silently testing stale behaviour. |
| 14 | **Agent** (`agent/graph.py`): a LangGraph `StateGraph` with `model ⇄ tools`. `interrupt()` pauses for SQL approval, and `Command(resume=…)` continues. An `InMemorySaver` checkpointer gives multi-turn threads. The step limit and recursion limit are both enforced. | **LangGraph vs a plain while-loop:** it gives a checkpointed state machine, so human-in-the-loop pause and resume and conversation threads come for free, and the flow is inspectable. **Approvals are collected *before* any tool runs,** because LangGraph re-executes the node on resume and tools must not run twice. |
| 15 | **MCP server** (`mcp_server.py`, official `mcp` SDK v2, `MCPServer`).<br>• Tools: `get_schema`, `run_sql`, `forecast_item`, `price_what_if`, `create_chart`, all backed by the **same `Toolbox`** as the LangGraph agent.<br>• A `retailpulse://schema` resource.<br>• Server `instructions`, and read-only tool annotations.<br>• Transports: stdio, plus Streamable HTTP with `--http`.<br>• Registered with Claude Code through the committed `.mcp.json`. | **Why MCP:** the tools become reusable by any MCP client (Claude Code, Claude Desktop, IDEs, other agents) without writing a new integration for each. Over MCP, *the client's* model is the agent, so the server ships the schema and usage hints itself (`get_schema`, `instructions`), since it can't rely on my system prompt. **One Toolbox for both front-ends** means the guardrails can't drift between the agent and MCP. |
| 16 | **Human approval over MCP**, with three paths:<br>• 2026-07-28+ clients: the tool returns an `InputRequiredResult` with an elicitation form, and the client retries carrying the answer.<br>• Older clients: a server-initiated `elicitation/create`.<br>• Clients without elicitation: a `ToolError` telling the model to ask the user and retry with `confirm_expensive=true`. | Each path is tested with a real in-process MCP client, for approve and deny. Graceful degradation matters because MCP clients vary widely in what they support. |
| 17 | **Eval suite** (`evals/questions.yaml`, `evals/graders.py`, `evals/run.py`). 25 questions:<br>• 12 SQL analytics, 3 inventory, 3 forecast accuracy<br>• 1 item forecast and 2 what-ifs<br>• 2 charts and 2 guardrail attacks<br>Gold answers are **computed at eval time** from gold SQL or tool calls. Metrics: answer accuracy, execution match, SQL validity, tool-selection accuracy, plus latency, tokens and cost. | **Computed gold, not hard-coded:** the same file grades the 105-series CI fixture and the 30k-series warehouse. **Deterministic graders instead of an LLM judge:** free, reproducible, and lenient on format ("$18.8 million", 12.3% vs 0.123, written dates) but strict on values (2%). **Execution match is a separate metric** from answer accuracy, so I can tell "fetched the wrong data" from "had the data, phrased it badly". |
| 18 | **Cassette keys ignore tool *outputs*.** | I record on Windows and CI replays on Linux, where LightGBM forecasts differ in the 6th decimal. Keying on tool outputs would make every replay a miss. Prompt, tool-definition and decision changes still invalidate the recording; data changes are caught because gold is recomputed. |
| 19 | **Agent HTTP API** (`api.py`):<br>• `/ask` and `/approve` handle approval as an HTTP round trip.<br>• `/ask/stream` and `/approve/stream` stream progress events over SSE (`tool_call`, `tool_result`, `answer` or `approval_required`).<br>• Reusing a `thread_id` asks a follow-up in the same conversation.<br>The agent gained `start` / `resume` / `stream`. | **Approval over HTTP:** the LangGraph checkpointer persists the paused run, so the next request can resume it. A thread with a pending approval returns 409 if asked something new. **Streaming is per step, not per token:** for an analytics agent, "running SQL…" progress matters more than token-by-token text. Token streaming would need a streaming LLM client. |
| 20 | **Observability** (`observability.py`):<br>• Always: one JSON log line per question (latency, tokens, cost, tools, stop reason).<br>• When keys are set: a Langfuse trace (agent span, then a generation per LLM call with usage and cost, then a tool span per call with SQL, row count and approval). | **Spans are created explicitly from the root,** not via implicit OpenTelemetry context, so nesting survives LangGraph worker threads and pause/resume across HTTP requests. **Testable offline:** `Langfuse(span_exporter=InMemorySpanExporter())` lets a test assert the trace tree without a server. |
| 21 | **Docker:**<br>• One image with three entrypoints (agent API :8000, forecast API :8001, MCP over HTTP :8002), built with uv and a cached dependency layer, running as a non-root user with a healthcheck.<br>• `docker-compose.yml` mounts the warehouse and model read-only.<br>• CI builds the image on every push. | **Model portability:** MLflow's registry stores absolute host paths (`C:/Users/...`), so a Linux container can't load `models:/…@champion`. `export_champion()` copies the champion into a self-contained folder and the service loads it via `RETAILPULSE_MODEL_DIR`. The registry handles promotion; serving uses an immutable artifact. |
| 22 | **CI** (`.github/workflows/ci.yml`): ruff, then pytest (fixture warehouse, no key), then the eval regression gate (replayed cassette vs `evals/baseline.json`), plus a Docker build. | The eval gate turns prompt and model changes into reviewed, measurable diffs. A prompt edit without re-recording fails loudly as a cassette miss. |
| 23 | **Baseline eval recorded** with `qwen2.5:7b`, a free local model run by Ollama on CPU, over 25 questions on the fixture warehouse:<br>• **answer accuracy 68%**<br>• execution match 61%<br>• SQL validity 53%<br>• tool selection 96%<br>Averages: 2.6 LLM calls and ~2 minutes per question. Total cost $0. The cassette is committed and the CI gate floors are set to these numbers (tolerance 0.05). | A 7B model on CPU is a deliberately weak, cheap baseline. It shows the harness works end to end and gives a measurable starting point. Every later change (prompt, schema notes, a stronger model) is judged against it. Replay reproduces the scores exactly in 33 s with no key. |
