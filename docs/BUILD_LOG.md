# Build Log

Chronological record of what was built, **why**, and which alternatives were rejected.
Read this before an interview to retell the story of the project.

| Step | What | Why / alternatives considered |
|------|------|-------------------------------|
| 1 | **Data warehouse.** Downloaded M5 (Kaggle `m5-forecasting-accuracy`). `retailpulse.data.ingest` reshapes the wide sales file (1,941 day columns) into a DuckDB star schema: `items`, `stores`, `calendar`, `prices`, `sales`. | **DuckDB** over Postgres/SQLite: it's embedded (no server), columnar and fast for analytics, and it reads CSV natively. A read-only connection is also a simple sandbox for the agent later. **The reshape runs in SQL (`UNPIVOT`), not pandas:** pandas `melt` on 59M rows needs several GB of RAM, while DuckDB streams it in 92s. **`revenue` is precomputed** in the fact table so the LLM doesn't need a three-way join for dollar questions. That means fewer chances for wrong SQL. |
| 2 | **Test fixture.** `scripts/make_fixture.py` cuts 105 series (3 stores × 5 items × 7 depts, last 730 days) in the *raw* M5 format (<1 MB). | Tests run the **real** ingest code on real-shaped data, so CI needs no Kaggle credentials and runs in seconds. The alternative was a mocked DB, but that wouldn't catch ingest bugs. |
| 3 | **Features** (`forecasting/features.py`): one DuckDB SQL query builds lags 28–56, 7/28/56-day rolling means, a 28-day std and zero-fraction, price ratio and week-over-week change, calendar/event/SNAP flags and item age. | **Direct 28-day strategy:** every feature looks ≥28 days back, so one model scores the whole horizon. The rejected alternative was a *recursive* model (lag-1 features, feeding predictions back), which compounds errors and needs 28 sequential calls at serving time. **Date-based `RANGE` windows** rather than row offsets, so gaps in a series can't shift a lag. **One query for train and serve**, which prevents training/serving skew without a feature store. |
| 4 | **Model** (`forecasting/train.py`): LightGBM, **Tweedie** objective, trained on 3 stores (one per state). The time split is train → 28-day validation (early stopping) → 28-day holdout → 28-day future. | **Tweedie vs MSE/Poisson:** retail demand is zero-inflated with a long tail. Tweedie (power 1.1) models that mass at zero and was the standard choice among top M5 solutions. **LightGBM vs deep learning (DeepAR/TFT):** it's faster to train on CPU, handles categoricals natively and is easy to explain, and gradient boosting won M5. **Two models:** *A* is trained without the last 56 days and gives an honest holdout score. *B* is refit on all data with A's best iteration count; it's the one deployed, so it uses the most recent demand. |
| 5 | **Evaluation:** WRMSSE (M5 metric, item×store level) plus MAE, RMSE and bias, compared with two baselines: a 28-day moving average and a 7-day seasonal naive. | A model is only worth deploying if it beats naive baselines. WRMSSE scales errors by each series' own volatility and weights them by revenue, so a 1-unit error on a $50 item matters more than on a $1 item. |
| 6 | **MLflow:** params, metrics, feature importance and the model are logged to a local SQLite store, and the model is registered as `retailpulse-demand`. The new version gets the **`champion` alias only if its holdout WRMSSE beats the current champion.** | This is a cheap version of a model-promotion gate. Serving loads `models:/retailpulse-demand@champion`, so promotion and rollback are alias moves with no code change. |
| 7 | **Forecasts published to DuckDB:** a `forecasts` table (backtest + future) and a `forecast_accuracy` view. | This lets the agent answer "how accurate was the forecast for FOODS in CA_1?" with plain SQL rather than a special tool. Only promoted models publish. |
| 8 | **Serving** (`forecasting/serve.py`): FastAPI with `/forecast` (item × store × ≤28 days) and `/what-if` (price change %). The model loads once at startup, and each request gets its own DuckDB cursor. | The what-if re-scores the horizon with the price features changed and history fixed, which approximates price elasticity *learned by the model*. It's a correlational estimate, not causal. |
| 9 | **Monotone price constraints, model v2.** Retrained with `monotone_constraints=-1` on the price features after v1's what-if produced backwards elasticities (see CHALLENGES #7). v2 was promoted by the champion gate. | **Results (3 stores, 9,147 series, 28-day holdout ending 2016-05-22):**<br>• WRMSSE: **0.823** model, 0.841 MA28, 1.076 seasonal naive.<br>• MAE 1.01, RMSE 1.97, bias −5.8%.<br>• Training takes ~6.5 min on a 12-core CPU, including 85 s of feature SQL. |
